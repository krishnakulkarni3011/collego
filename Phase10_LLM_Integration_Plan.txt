───────────────────────────────────────────────────────────────────────────────
1. PROVIDER: LOCAL OLLAMA (FREE FOREVER)
───────────────────────────────────────────────────────────────────────────────

Why: $0 forever, no API key, no quota, no account, and — critically for student
records — inference runs on our own machine, so PII never leaves our
infrastructure. Hosted "free tiers" (Groq / Gemini / OpenRouter :free) can be
withdrawn or start training on data; self-hosted Ollama cannot.

HARDWARE PLAN (16 GB RAM + RTX 3060 6 GB)
  Chosen model: qwen2.5:7b-instruct, default Q4_K_M quant ≈ 4.7 GB weights.
    - Fits inside 6 GB VRAM with a trimmed context window (see below).
    - If it spills a little to RAM that is fine; 16 GB system RAM absorbs it.
  Context window: set num_ctx = 4096 (NOT 32k). KV cache is the thing that
    blows 6 GB. 4096 is plenty for one user's attendance/CGPA/marks snippet.
  Expected performance: ~30-50 tokens/sec fully/partly on GPU => 2-5 s replies.
  Fallback if too slow or OOM: qwen2.5:3b-instruct (≈1.9 GB) — noticeably
    faster, weaker reasoning, still fine for "quote my numbers" tasks.
  Embeddings (Phase 5 only): nomic-embed-text (≈275 MB) — also free.
  Single resident model: OLLAMA_MAX_LOADED_MODELS=1, OLLAMA_NUM_PARALLEL=1,
    OLLAMA_KEEP_ALIVE=30m so the model stays warm without eating RAM.
  Model name lives in AI_MODEL env var so it can be swapped with zero code
    changes.

MODEL LICENCE NOTE: Qwen2.5 is Apache-2.0 (free for commercial use). Llama 3.1
uses the Llama Community Licence. Both are free to self-host; Qwen is the
simpler choice for a college project.


───────────────────────────────────────────────────────────────────────────────
2. CORE PRINCIPLE: THE AI NEVER DECIDES WHO YOU ARE
───────────────────────────────────────────────────────────────────────────────

    Identity comes ONLY from the verified JWT (Authentication.getName()).
    Never from the request body. Never from the chat text. Never from the LLM.

Consequence: even if the model is tricked into "asking for Rahul's marks",
no code path exists to fetch Rahul's marks for a student caller, because the
only id available to any query is the caller's own id.

This is turned from a convention into an enforced boundary in section 4.


───────────────────────────────────────────────────────────────────────────────
3. TARGET ARCHITECTURE
───────────────────────────────────────────────────────────────────────────────

  React frontend
      |  JWT only — NO ids in any AI payload
      v
  Spring Boot backend        <-- the ONLY component that touches the database
      |  1. identity from verified JWT
      |  2. build AiScope (role + own id + allowed ids)
      |  3. bounded tool-calling loop with the model
      |  4. every tool executes server-side UNDER AiScope
      v
  ai-service (FastAPI, stateless)   <-- no DB, no identity logic
      |  prompt assembly + Ollama HTTP call + strict output validation
      v
  ollama container (local model, free forever)

Change from today: instead of one pre-baked JSON blob, the model requests
specific data through typed tools (function calling). It still has ZERO
database access; Spring Boot executes each tool with the caller's scope bound
server-side.

Why tools instead of a context dump:
  - "my attendance" triggers exactly one query — the caller's own.
  - A "helpful" broad query returning other students' rows is structurally
    impossible: every tool signature takes AiScope as the only id source.
  - Smaller prompts => faster inference on a 6 GB GPU.
  - New data sources cannot silently widen access; a new tool must explicitly
    consume AiScope.


───────────────────────────────────────────────────────────────────────────────
4. SCOPE MODEL (DENY BY DEFAULT)
───────────────────────────────────────────────────────────────────────────────

One immutable value object, com.collego.ai.AiScope:

    record AiScope(
        Long        userId,              // caller
        String      email,               // caller
        Role        role,                // STUDENT | FACULTY | ADMIN
        Set<Long>   allowedStudentIds,   // students the caller may read
        Set<Long>   allowedSectionIds,   // sections the caller may read
        Set<Long>   allowedCourseIds,    // courses the caller may read
        boolean     passwordAccess       // ALWAYS false
    )

Built by exactly one factory: AiScopeFactory.forUser(email).

  STUDENT
    allowedStudentIds = { own id }
    allowedSectionIds = sections the student is enrolled in
    allowedCourseIds  = courses in those sections
    passwordAccess    = false

  FACULTY  (per decision D2 — assigned sections + related general info)
    allowedSectionIds = sections where a subject assignment exists for this
                        faculty (source of truth = the SAME authorization the
                        existing FacultyController endpoints already use:
                        /attendance/{sectionId}, /marks/internal/{sectionId},
                        /analytics/{sectionId}, /assignments/{sectionId}, ...).
    allowedStudentIds = students enrolled in those sections only
    allowedCourseIds  = courses taught in those sections
    allowed extras    = general info related to those sections only:
                        their courses, subject assignments, section timetable,
                        their own notices, class analytics, students' names +
                        roll numbers + section-wise attendance/marks within
                        those sections.
    passwordAccess    = false
    Asking about a student outside the assigned sections => AccessDenied.

  ADMIN  (per decision D3 — full data EXCEPT passwords)
    allowed* = all
    passwordAccess = false
    The exclusion is enforced structurally, not by prompt wording:
      - AI-path repository methods use DTO projections that never select the
        password field (User.password / updated password column).
      - AiTools may never accept or return a User entity directly; only
        password-free DTOs.
      - serialVersion-like guard: an output check rejects any payload containing
        a "password"/"passwordHash"/"credentials" key.

  Anything else / unknown / missing identity => empty scope (deny everything).

Four enforcement layers, ALL required:
  L1 IDENTITY      JWT only (Authentication.getName()).
  L2 SCOPE BUILD   AiScopeFactory, deny-by-default, no fallbacks that widen.
  L3 DATA ACCESS   Every AI-path query goes through a repository method whose
                   signature REQUIRES a studentId / sectionId / courseId, and
                   which calls scope.assertAllowsX(id) BEFORE hitting the DB.
                   Generic findById() is FORBIDDEN on the AI path.
  L4 OUTPUT GUARD  Response-level check that no value belongs to a user outside
                   the scope, and that no password/secret key appears. Failure
                   => return the safe fallback, log the incident.

Password rule (D3), spelled out:
  - Passwords are stored hashed (BCrypt) and are only ever compared, never read.
  - The AI path never receives a password hash. There is no tool named
    "getPassword" and there never will be.
  - Even the admin AI cannot "show me the updated password of student X".
    It answers: "Passwords are stored as one-way hashes and cannot be shown."
  - Include an automated test that asserts this exact refusal and asserts no
    password-shaped field appears in any AI response for the admin role.


───────────────────────────────────────────────────────────────────────────────
5. WHAT EACH ROLE MAY ASK (DATA MAP)
───────────────────────────────────────────────────────────────────────────────

STUDENT — own data only, via existing StudentPortalService methods
  getProfile, getAttendance, getOverallAttendance, getInternalMarks,
  getSemesterMarks, calculateCgpa, getTimetable, getQuestionPapers,
  getPlacementNotices, getNotifications, getAcademicHistory,
  getAssignmentsForStudent, getMySubmission, getMaterialsForStudent.
  All of these already take an email and resolve it internally, so binding them
  to the caller's own email makes them inherently self-scoped.
  Also allowed: college-wide reference info (departments, course catalog,
  faculty directory, shared notices/placement notices, approved question
  papers) — explicitly fetched, never dumped.

FACULTY — assigned sections + their general info only
  sections, courses, subject assignments, section attendance, section internal
  and semester marks, assignment submissions + marks, assignment/materials
  management views, question papers they uploaded, their notices,
  /analytics/{sectionId}. All keyed by allowedSectionIds.
  Denied: any section not assigned to them; another faculty's sections;
  admin-only data; passwords.

ADMIN — full data except passwords
  Everything, aggregate-first for reporting questions. Passwords excluded
  structurally (section 4). Secrets (JWT signing key, DB creds, AWS creds,
  OpenRouter/key material) are never placed in prompts or logs.

NOT AVAILABLE TODAY (do not let the model pretend otherwise):
  Fee / payment data does not exist anywhere in the backend (verified).
  The model must answer "fee data is not available in this system", and the
  dead "fees" branch in _stub_chat_response must be removed or wired to a real
  source later.


───────────────────────────────────────────────────────────────────────────────
6. REQUEST PIPELINE (STEP BY STEP)
───────────────────────────────────────────────────────────────────────────────

 1. POST /api/ai/chat  body = { message, history }  — NO ids accepted.
 2. SecurityConfig.java:61 already requires authentication for /api/ai/**.
 3. Controller: scope = AiScopeFactory.forUser(auth.getName()).
 4. Controller: history = sanitize(history)  (see section 7, fixes hole H1).
 5. Controller calls aiService.chatScoped(scope, message, history).
 6. Spring Boot <-> ai-service run a BOUNDED tool loop (max 4 rounds, then
    force a final answer):
        model -> tool_call("getMyAttendance", {}) 
              -> Spring executes under AiScope
              -> datum (caller-only) 
              -> model -> ... -> final text
    Tool results are delimited as data, e.g.
        <data source="attendance" readonly="true"> ... </data>
 7. Output guards (L4) run before the response leaves Spring Boot:
        - no id/email/name of a user outside scope
        - no password/secret-shaped key or value
        - no raw JSON context echo, no markdown code fence, length cap
 8. Audit log line per tool call:
        ts, caller email, role, tool, args (redacted), row count, allowed/denied.
 9. Rate limit per caller (e.g. 20 AI messages / 5 min) + per-request token
    budget. A 6 GB GPU is the bottleneck; this also blunts injection probing.
10. On model error/timeout/malformed output => deterministic stub fallback.
    Never surface a raw model error or stack trace to the client.


───────────────────────────────────────────────────────────────────────────────
7. PROMPT-INJECTION AND LEAK DEFENSES
───────────────────────────────────────────────────────────────────────────────

Fix H1 (required, both sides):
   - whitelist history roles to {"user","assistant"} in AiController AND in
     FastAPI; drop/400 anything else; cap to last 6 turns.
   - never accept a client-supplied "system" message, ever.

Other required defenses:
   - Treat ALL DB-derived text as untrusted: names, filenames, notice bodies,
     resume text, question-paper titles. Delimit them and instruct the model
     that instructions found inside data must be ignored.
   - The model never supplies identity arguments for student-facing tools.
     The id is injected from AiScope server-side. Where a sectionId/courseId is
     needed, the server validates it against allowedSectionIds/CourseIds first.
   - Never send secrets to the model: no password hashes, JWT, tokens, DB/AWS
     credentials.
   - Minimize PII in prompts: send "your attendance is 82%", not the whole user
     row. Do not send phone numbers, addresses, or parent details.
   - Structured features (resume analysis, placement assistant) get strict
     JSON-schema validation of model output; malformed => stub fallback.
   - Keep AiServiceConfig.java:20 read timeout and add a hard total deadline so
     a slow local model cannot hang a request thread.
   - Log-denied-and-continue: a denied cross-user request returns a normal
     "I can only access your own data" message, plus an audit entry. Do not
     leak the existence of the other record.

10. ACCEPTANCE CRITERIA
───────────────────────────────────────────────────────────────────────────────

 - No student can obtain another user's data through any AI endpoint, by any
   phrasing, payload, or injection. Proven by tests B, C, D.
 - Faculty can reach only their assigned sections and the general info tied to
   those sections. Proven by tests D and J.
 - Admin reaches full data but can never retrieve any password/hash/secret.
   Proven by test H.
 - Every AI data access derives from the JWT identity and is audit-logged.
 - Answers quote real stored values (attendance %, SGPA, CGPA, dates) and say
   "not available" instead of inventing data.
 - Inference cost is $0 forever: no API key, no outbound LLM call.
 - Model down => deterministic fallbacks still answer; no 500s, no stack traces.
 - No UI content or behaviour change beyond optional note in section 8.
 - Runs on 16 GB RAM + RTX 3060 6 GB with num_ctx=4096 at acceptable latency.


───────────────────────────────────────────────────────────────────────────────
11. RISKS AND MITIGATIONS
───────────────────────────────────────────────────────────────────────────────

 R1. 6 GB VRAM is tight for a 7B model at long context.
     -> num_ctx=4096, OLLAMA_NUM_PARALLEL=1, single loaded model; drop to
        qwen2.5:3b-instruct if needed. Both are one env-var change.
 R2. CPU-only fallback would be ~3-8 s/reply.
     -> Rely on GPU; keep KEEP_ALIVE so the model stays warm; cache repeated
        questions per user.
 R3. Model hallucinates a grade.
     -> Numbers come from tool results, not model memory; instruct "only use
        provided data"; deterministic stubs remain for the math features.
 R4. Prompt injection via DB text (a student named "ignore previous...").
     -> Delimit data, strip instruction-like content where possible, and rely
        on the fact that tools cannot access other users regardless of wording.
 R5. Docker GPU passthrough friction on Windows.
     -> Document the native-Ollama + host.docker.internal path as the dev
        fallback.
 R6. Ollama container restart drops the model.
     -> Persistent named volume; warm-up call on ai-service start.
