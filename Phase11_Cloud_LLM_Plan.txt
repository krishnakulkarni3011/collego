0. WHY THIS CHANGE
--------------------------------------------------------------------------------
Phase 10 ran the LLM on the workstation through Ollama. It worked, but it cost
9.6 GB of local disk (3 models + the Ollama runtime with CUDA) on a 16 GB /
RTX 3060 Laptop machine, and a local 7B on that hardware took 1.6-15 s per
answer. Ollama has been uninstalled and every model deleted.

Phase 11 keeps the part of Phase 10 that was genuinely valuable — the per-user
data isolation, the tool-calling layer, the output guard, the audit trail — and
moves only the inference to a cloud provider's free tier. Nothing is stored
locally any more, and the answer latency drops to ~1-3 s.

Decisions taken with the project owner:
  D1. Provider     : Groq (free tier, no credit card required).
  D2. Scope        : Track B — re-apply the full Phase 10 isolation layer on
                     top of the cloud provider (not the minimal path).
  D3. Student PII  : acceptable to reach Groq. Groq does not retain inference
                     data by default and offers Zero Data Retention. Only the
                     rows needed for the question are ever sent.
  D4. "Free"       : best-effort. Free tiers change — Groq retired
                     llama-3.3-70b-versatile from its free tier on 2026-08-16.
                     The provider abstraction, fallback provider, circuit
                     breaker and deterministic stubs mean a tier change
                     degrades answer quality, never breaks the app.
  D5. Local models : none. The `ollama` compose service is removed entirely.


1. ARCHITECTURE
--------------------------------------------------------------------------------
  Browser
    |  JWT — identity is taken from the token and nowhere else
    v
  Spring Boot :8081
    |  AiScopeFactory      who may see what (deny by default)
    |  AiToolCatalog       the model asks for data; Spring queries the DB
    |                      UNDER the caller's scope and returns the result
    |  AiOutputGuard       blocks secrets, foreign emails and enrolment numbers
    |  AiRateLimiter       per-user budget
    |  AiAuditLogger       every call and denial -> audit_logs
    v
  ai-service :8000
    |  provider abstraction: groq | openrouter | openai | gemini
    |  circuit breaker + daily call budget + optional fallback provider
    |  LLM_API_KEY lives here and nowhere else
    v
  Groq   https://api.groq.com/openai/v1/chat/completions
         (OpenAI-compatible wire format, Bearer auth)

  Fallback path — no key / 429 / provider down / daily budget spent:
    ai-service -> deterministic Phase 9 stubs. The UI always answers.

The API key never reaches the browser: browser -> backend -> ai-service ->
provider. The backend never talks to the provider directly.

3. PROVIDER LAYER (ai-service/main.py)
--------------------------------------------------------------------------------
3.1 Configuration
    PROVIDER            groq              (env LLM_PROVIDER)
    LLM_BASE_URL        https://api.groq.com/openai/v1   (env LLM_BASE_URL)
    LLM_API_KEY         from the secret store            (env LLM_API_KEY)
    DEFAULT_MODEL       openai/gpt-oss-120b              (env LLM_MODEL)
    FALLBACK_*          optional second provider
    DAILY_CALL_BUDGET   8000                             (env AI_DAILY_CALL_BUDGET)
    CIRCUIT_BREAKER_SECS 300                             (env CIRCUIT_BREAKER_SECONDS)
    AI_ENABLED          true                             (env AI_ENABLED)

    base_url is everything up to (not including) /chat/completions, so the same
    code serves Groq (…/openai/v1), OpenRouter (…/api/v1) and OpenAI (…/v1).

3.2 Model
    openai/gpt-oss-120b  (primary — strong tool calling and instruction following)
    qwen/qwen3.6-27b     (fallback)
    openai/gpt-oss-20b   (fastest, weakest)
    NOTE: llama-3.3-70b-versatile is no longer on Groq's free tier.

3.3 Failure handling — every path degrades to the stubs
    no API key .................. _ProviderUnavailable -> stub
    AI_ENABLED=false ........... _ProviderUnavailable -> stub
    daily budget exhausted ..... _ProviderUnavailable -> stub
    circuit breaker open ....... _ProviderUnavailable -> stub
    HTTP 429 ................... breaker trips (300 s) -> fallback provider
                                  -> stub
    HTTP 5xx ................... breaker trips -> fallback provider -> stub
    connection refused ......... breaker trips -> fallback provider -> stub
    HTTP 4xx (bad request) .... stub (not the provider's fault, no retry)

3.4 JSON mode
    Features 2, 5, 6 and 7 ask for JSON. If the provider rejects
    response_format=json_object (HTTP 400 mentioning response_format), the call
    is retried once without it and the response is parsed leniently.

3.5 Embeddings
    Groq has no embeddings endpoint. The /embed endpoint therefore returns an
    empty result and the Phase 5 RAG uses the keyword ranker that is already
    implemented (60 s backoff so an absent embedding model costs nothing).
    An optional EMBED_PROVIDER can be added later without changing the caller.


4. QUOTA PROTECTION
--------------------------------------------------------------------------------
The free tier is shared by the whole college, so it is protected on four
levels:

  per user        AiRateLimiter      30 requests / 5 minutes
  per question    90 s response cache (identical questions cost nothing)
  per question    tool rounds capped at 3 (max ~4 provider calls per question)
  per instance    daily call budget  8000 of Groq's 14,400/day
  per instance    circuit breaker    5 minutes open after a 429 or a 5xx run

  Modelling: 128 users x 20 questions/day x ~3 provider calls = ~7,700 calls,
  which fits inside the budget with headroom.

  When the budget is spent the log line is explicit — it is never silent.

10. RISKS
--------------------------------------------------------------------------------
  Risk                       | Mitigation
  -------------------------- | ---------------------------------------------
  Free tier changes          | abstraction + fallback provider + stubs; the
                             | app degrades in quality, never fails
  429 during a class demo    | circuit breaker + cache + stubs; the UI
                             | still answers
  Provider outage            | breaker -> stubs
  Latency                    | Groq serves at 500+ tok/s (~1-3 s per call)
  Cost                       | $0 inside the quota
  Key leakage                | key lives only in the ai-service env; never in
                             | the browser, never in git
  Student PII at the provider| Groq does not retain inference data (ZDR
                             | available); only the rows needed per question
                             | are sent, and the AI never receives a password
                             | hash, token or refresh token
