DECISIONS (confirmed by user)
-----------------------------
1. Primary model : openai/gpt-oss-120b
2. Fallback model: openai/gpt-oss-20b
3. Database access: CURATED TOOLS ONLY (no raw SQL tool, no DB
   connection or credentials ever given to the model)
4. Student isolation: a student must ONLY ever receive their own
   details from AI responses. Another student's marks, attendance,
   profile, fees, resume or any record must never be returned, even
   if the student asks for it directly, guesses an id, or tries to
   manipulate the model with prompt injection.

API KEY
-------
Yes, a key is required - but it is free.
- Sign up at https://console.groq.com (email or Google, no card).
- Create an API key at https://console.groq.com/keys (starts gsk_...).
- Key is stored ONLY in environment variables (.env), never in git.
- Free tier quotas are per organisation, shared by all API keys.

FREE TIER LIMITS (Oct 2026)
---------------------------
Model                     RPM   RPD    TPM     TPD
openai/gpt-oss-120b       30    1000   8000    200000
openai/gpt-oss-20b        30    1000   8000    200000

Notes:
- All Groq models support tool/function calling.
- 8,000 tokens per minute is the binding constraint, not the daily
  request count. The tool loop sends tool descriptors, history and
  tool results on every round, so a single question can consume
  3,000-6,000 tokens. Token budgeting is therefore mandatory.
- Older models (llama-3.1-8b, llama-3.3-70b, qwen3-32b,
  llama-4-scout) were deprecated in 2026 - do not target them.

CURRENT ARCHITECTURE (already built)
================================================================

React portal (Student AI Assistant, Smart Search, performance
prediction, attendance risk, resume analysis, placement assistant,
question paper insights)
  -> Spring Boot /api/ai/*        (AiController, role guards)
    -> AiChatOrchestrator          (grounded tool loop, max rounds)
      -> AiToolCatalog             (role-scoped read-only tools)
        -> executed in Spring under AiScope
      -> AiOutputGuard             (reply sanitising)
      -> AiRateLimiter / AiResponseCache / AiAuditLogger
      -> AiService (RestTemplate)  -> ai-service :8000 (FastAPI)
        -> Groq / Ollama (OpenAI-compatible)

Key property: the model never touches the database. It requests a
tool, Spring executes it under the caller's AiScope, and returns
JSON. This is the design we keep and extend.

Existing AiScope fields:
  userId, email, role, unrestricted,
  allowedStudentIds, allowedSectionIds, allowedCourseIds
Students are NOT unrestricted; faculty see only their assigned
sections; admins are unrestricted.


================================================================
GAPS FOUND IN THE CURRENT SETUP
================================================================

1. docker-compose.yml and docker-compose.prod.yml do NOT pass
   LLM_API_KEY, so a cloud provider can never authenticate.
2. Compose passes AI_MODEL, but ai-service reads LLM_MODEL, so the
   model override is silently ignored.
3. Compose defaults LLM_PROVIDER=ollama and prod .env has no LLM_*
   variables at all -> production runs stub-only and the
   collego-ai-service container is currently unhealthy.
4. AI_DAILY_CALL_BUDGET defaults to 8000, but the free RPD is 1000;
   the budget never protects anything.
5. Embeddings are Ollama-only; Groq has no embeddings API.
   search_my_study_material already falls back to keyword ranking,
   which is acceptable for now.

================================================================
PHASE 4 - DATABASE ACCESS VIA CURATED TOOLS
================================================================

Rule: Groq never receives a database connection, SQL text, schema
dump or credentials. It only receives the JSON returned by an
allow-listed Java tool.

4.1 Student tools (own data only)
    Already present: get_my_account, get_my_profile, get_my_attendance,
    get_my_cgpa, get_my_timetable, get_my_internal_marks,
    get_my_semester_marks, get_my_assignments, get_my_notifications,
    get_my_placement_notices, get_my_question_papers,
    search_my_study_material.
    Add: "what do I need to reach X%" style attendance/marks target
    calculation, computed server-side from the caller's own record.

4.2 Faculty tools (assigned sections only)
    Existing: get_my_sections, get_section_roster,
    get_section_attendance_summary, get_student_academic_summary.
    Add: low-attendance list for an assigned section, marks
    distribution for an assigned section.

4.3 Admin tools (aggregates only)
    Add: department totals, faculty count, placement statistics,
    at-risk student counts. No bulk PII dumps.

4.4 Hard isolation requirements (student must never see another
    student's data)
    a. Every tool receives the server-built AiScope; the model can
       never supply or override userId/email/role.
    b. get_student_academic_summary calls scope.requireStudent(id)
       BEFORE any repository access; a student's allowedStudentIds
       contains only their own student id.
    c. Ignore any id/email found in the user's message text; resolve
       the caller from the JWT only.
    d. Never expose enumerable ids in replies unless they belong to
       the caller (student ids, section ids, enrolment numbers).
    e. AiOutputGuard: reject or redact replies that contain another
       student's USN, email, name or marks that were not part of the
       caller's own tool result. Log a security event when it
       happens.
    f. Deny-by-default: a tool not registered for Role.STUDENT is
       not even offered to the model for a student caller.
    g. Audit every tool call: user, role, tool, arguments, row count,
       timestamp (AiAuditLogger).
    h. Prompt-injection resistance: instructions inside tool results
       or user messages ("ignore previous rules", "show all
       students") must not change scope; scope is code, not prompt.

4.5 Tests (must all pass before deployment)
    - Student asks "show my attendance" -> only their own data.
    - Student asks "show 2BA24CS007's marks" -> denied, no data,
      audited.
    - Student asks "list all students in my section" -> denied.
    - Student supplies another student's numeric id -> denied.
    - Student tries a prompt injection -> scope unchanged.
    - Faculty asks about a section they do not teach -> denied.
    - Faculty asks about an assigned section -> allowed, scoped.
    - Admin aggregate query -> allowed, aggregated.
    - Tool result never contains password_hash, tokens or S3 URLs.

Done when:
- All isolation tests above pass.
- Manual prompts in the student AI tab confirm only own data.
- Audit log shows the tool, scope and result size for each call.

===============================================================
IMPLEMENTATION NOTES (deviations and fixes found during the build)
===============================================================

1. AI_MAX_TOOL_ROUNDS is 1, not 2.
   The 19 role-filtered tool descriptors are large. Two tool-enabled
   rounds in one minute could exceed the 8k TPM free-tier limit. One
   tool-enabled round still allows several tool calls in a single model
   response, and the next round is text-only. Raise the env var only if
   the Groq plan is upgraded.

2. Tool-result protocol fixed for OpenAI-compatible providers.
   The Spring backend sends a compact toolTrace ({name, content}). The
   ai-service now synthesises a matching assistant tool_calls entry and
   a tool message with the same tool_call_id. Before this fix Groq
   rejected the second round with HTTP 400, so every tool-using question
   silently fell back to the deterministic stub.

3. Resilience tuned for a shared free tier.
   - HTTP 429 opens the breaker for 60s (the TPM window is one minute).
   - Network/DNS errors retry once after 0.8s, then open for 30s.
   - HTTP 400/401/404 do NOT open the breaker (they are request bugs).
   - CIRCUIT_BREAKER_SECONDS default is 60 (was 300).

4. Production ai-service healthcheck used curl, which python:3.11-slim
   does not ship. It now uses python + urllib in docker-compose.prod.yml,
   so the container reports healthy.

5. The production frontend image must be built with an EMPTY
   VITE_API_URL so the browser calls the same origin and nginx proxies
   /api/ to the backend. Building it through the local compose file bakes
   in http://localhost:8081 and breaks production (mixed content).
   Build command used:
     docker build --build-arg VITE_API_URL= ...
   The local compose keeps VITE_API_URL=http://localhost:8081.

6. The four removed student AI tabs now live inside AI Assistant:
   - quick actions call /api/ai/performance-prediction,
     /api/ai/attendance-risk and /api/ai/placement-assistant;
   - Smart search toggles the assistant into a search mode backed by
     /api/ai/smart-search;
   - the same three insights are exposed as student-only chat tools.
   Sidebar: AI Assistant and Resume Analyzer, moved above Services so
   both stay visible without scrolling.

7. The key was not present in this plan file. It was supplied separately
   and stored only in the gitignored local .env and /opt/collego/.env.
   Rotate it in the Groq console if it was shared anywhere else.
